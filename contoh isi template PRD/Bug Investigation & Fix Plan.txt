# Bug Investigation & Fix Plan

Desc:
Structured document for investigating, diagnosing, and fixing a bug. Covers symptoms, reproduction, root cause analysis, proposed fix, and verification — useful for complex bugs that need clear documentation.

Instructions: Write this like an engineering investigation report — factual, precise, and evidence-based. Reproduction steps should be exact (click this, type that, see this error). Root cause analysis should trace the actual code path that fails, not speculate. The proposed fix should be specific enough for an AI coding assistant or engineer to implement directly. Include what NOT to do if there are tempting but wrong fixes. The test plan should verify the fix works and confirm nothing else broke.

Template Sections                                                     7 sections

## Bug Summary
### Overview
What is happening in 1-2 sentences — describe the broken behavior, not the fix.

### Metadata
- **Severity**: Critical / High / Medium / Low
- **Affected users**: Percentage or count, and which segments
- **First observed**: Date and how it was discovered
- **Environment**: Production / Staging / Both
- **Error tracking**: Link to Sentry issue, LogRocket session, or relevant logs

### Business Impact
What is the cost of this bug remaining unfixed? Revenue loss, blocked users, trust erosion, support load, etc.

## Reproduction Steps
Exact numbered steps to reproduce, starting from a clean state.

### Steps
1. Go to [URL/page]
2. Log in as [role/account type]
3. Click [element] / Enter [input]
4. Observe [broken behavior]

### Environment Details
- **Browser/device**: Chrome 120 on macOS, Safari on iOS 17, etc.
- **Account type**: Admin, free user, new signup, etc.
- **Required data**: Specific data conditions needed to trigger the bug
- **Frequency**: Always reproducible / Intermittent (describe conditions that increase likelihood)
- **Timing**: Any time-dependent or sequence-dependent factors

## Expected vs. Actual Behavior
### Expected Behavior
What SHOULD happen according to the spec, design, or previous working state. Reference the source of truth (Figma, PRD, previous release).

### Actual Behavior
What ACTUALLY happens. Be precise:
- **Visual**: What the user sees (include screenshots)
- **Console**: Any errors in browser console or server logs
- **Network**: Failed requests, unexpected responses, status codes
- **Data**: Any data corruption, missing records, or incorrect state

### What Still Works
Note any related functionality that is NOT broken — this helps narrow the root cause.

## Root Cause Analysis
### Investigation Trail
What was checked and ruled out during debugging:
1. Checked [hypothesis A] → Ruled out because [evidence]
2. Checked [hypothesis B] → Found the issue here

### Root Cause
- **File**: Exact file path and function/line
- **What happens**: Trace the code path from user action to failure
- **Why it fails**: The specific logic error, missing check, race condition, or data issue
- **When it was introduced**: Regression from [PR/commit]? Always existed? Data-dependent?

### Contributing Factors
Anything that made this bug possible: missing tests, unclear spec, tech debt, etc.

## Proposed Fix
### Recommended Approach
- **Files to modify**: List each file and the change needed
- **Logic change**: Describe the fix at a code-concept level
- **Why this is correct**: Explain why this fix addresses the root cause

### Alternative Approaches
If there are other ways to fix this:
- **Option B**: Description, with pros/cons vs. recommended approach
- **Option C**: Description, with pros/cons

### Risks
- Could this fix break anything else?
- Any performance implications?
- Does this need a database migration or data backfill?

## Test Plan
### Manual Verification
1. Follow reproduction steps → Bug no longer occurs
2. [Additional manual check]
3. [Edge case verification]

### Automated Tests to Write
- **Unit test**: Test the specific function/logic that was fixed
- **Integration test**: Test the API endpoint or data flow end-to-end
- **E2E test**: Test the user flow if this is a critical path

### Regression Checks
- Verify [related feature A] still works correctly
- Verify [related feature B] still works correctly
- Monitor error tracking (Sentry) for 24-48 hours post-deploy
