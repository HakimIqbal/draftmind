# Database Schema Design

Desc:
Plan your data model, relationships, indexes, and migrations before AI generates them. Prevents costly rework by thinking through entities, access patterns, and constraints upfront.

Instructions: Write this as a precise technical reference for building the database. Entity definitions should list actual field names with types (e.g., id: uuid, email: text, createdAt: timestamptz). Relationships should be explicit about cardinality and foreign keys. Access patterns should describe real queries the app will run. Be opinionated about index choices and explain the tradeoffs. Use the user's stated database technology (Postgres, MySQL, MongoDB, etc.).

## Overview & Goals
What data this system manages and the key design priorities.

### Database Choice
- **Technology**: PostgreSQL, MySQL, MongoDB, SQLite, etc.
- **Hosting**: Neon, Supabase, PlanetScale, self-hosted, etc.
- **Rationale**: Why this database fits the use case

### Design Priorities
- **Read vs. write heavy**: Which matters more?
- **Consistency model**: Strong consistency vs. eventual
- **Normalization**: Normalized, denormalized, or hybrid
- **Scale expectations**: Expected row counts and query volume

## Core Entities
Define every table or collection with all fields.

### Format
```
TableName
- id: uuid (PK, default: gen_random_uuid())
- fieldName: type (constraints)
- fieldName: type (nullable, default: value)
- createdAt: timestamptz (default: now())
- updatedAt: timestamptz
```

### Field Annotations
- **PK**: Primary key
- **FK**: Foreign key (reference: Table.field)
- **UQ**: Unique constraint
- **IDX**: Indexed
- Mark required vs. nullable fields explicitly

Group related entities together (e.g., User entities, Content entities, Billing entities).

## Relationships & Constraints
### Relationship Map
List every relationship between entities:
- **One-to-one**: User → UserProfile
- **One-to-many**: User → Post (user has many posts)
- **Many-to-many**: User ↔ Organization (via Membership table)

### Foreign Key Behavior
For each FK, specify:
- **ON DELETE**: CASCADE, SET NULL, RESTRICT, or NO ACTION
- **ON UPDATE**: CASCADE or NO ACTION

### Constraints
- **Unique constraints**: e.g., (orgId, email) must be unique together
- **Check constraints**: e.g., price > 0, status IN ('active', 'archived')
- **Business rules**: Any logic enforced at the DB level

## Indexes & Performance
### Required Indexes
For each index beyond primary keys:
- **Table.column(s)**: Index type, which query it supports

### Example
```
Post.authorId — B-tree, for filtering posts by author
Post.(status, createdAt) — Composite, for listing active posts sorted by date
Post.title — GIN (trigram), for full-text search
```

### Performance Considerations
- Queries expected to be slow or complex
- N+1 risks and how to prevent them (eager loading, joins)
- Pagination strategy (cursor-based vs. offset)
- Caching approach for frequently read data

## Access Patterns
Describe the most common queries the application will run.

### Format
```
Pattern: List all projects for a user
Query: SELECT * FROM Project WHERE ownerId = ? ORDER BY createdAt DESC
Frequency: Very high (every page load)
Indexes used: Project.ownerId
```

### Categories
- **High-frequency reads**: Dashboard, lists, lookups
- **Writes**: Creates, updates, deletes
- **Complex queries**: Aggregations, reports, search
- **Background jobs**: Scheduled queries, batch processing

## Migration Plan
### Migration Tool
- **Tool**: Prisma Migrate, Drizzle Kit, Knex, raw SQL, etc.
- **Workflow**: How migrations are created, reviewed, and applied

### Seed Data
- Development seed data for testing
- Required production seed data (roles, default settings, etc.)

### Evolution Strategy
- Approach to zero-downtime migrations in production
- Column rename/removal process (add new → migrate data → remove old)
- Data backfill procedures for new required columns

## Security & Privacy
### Sensitive Data Inventory
Identify every field containing sensitive data:
- **PII**: email, name, phone, address
- **Credentials**: password hashes, API keys, tokens
- **Financial**: payment info, billing addresses

### Protection Measures
- **Encryption at rest**: Database-level or column-level
- **Hashing**: Which fields (e.g., passwords with bcrypt/argon2)
- **Row-level security**: If applicable, describe RLS policies

### Compliance
- **Data retention**: How long data is kept, auto-deletion policies
- **Right to deletion**: Process for GDPR/CCPA delete requests
- **Audit logging**: Which operations are logged
