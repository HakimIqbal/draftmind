# Refactoring Plan

Desc:
Plan a codebase refactor with clear motivation, target architecture, migration steps, and risk assessment. Keeps large refactors organized and prevents the common trap of refactoring without a finish line.

Instructions: Write this as a pragmatic engineering plan, not an aspirational architecture doc. The current state section should be honest about what is actually wrong — with specific examples of pain points, not vague complaints. The target state should be concrete enough to validate when you're done. Migration steps should be ordered so each step leaves the codebase in a working state. Timebox the effort — refactors without deadlines never finish. Be explicit about what is NOT being refactored.

Template                                          7 Sections 

## Current State
What exists today and what is specifically wrong with it.

### Problem Areas
For each problem, be concrete:
- **Area**: [Module/file/pattern]
- **What's wrong**: [Specific issue — not 'it's messy' but '3 different auth patterns across 12 files']
- **Impact**: [Build time, error rate, developer confusion, incidents caused]

### Quantified Pain
- Build/deploy time: X minutes
- Incident frequency: X per month related to this area
- Developer hours wasted: X hours/week
- Code duplication: X instances of similar logic

## Target State
What the code looks like when the refactor is done.

### Architecture Changes
Describe the new patterns, abstractions, or structure at a level specific enough to know when you're done.

### Before → After
- **Before**: [Current pattern with specific example]
- **After**: [New pattern with specific example]

### Completion Criteria
Objectively verifiable — not 'code is cleaner' but:
- [ ] All API routes use the new middleware pattern
- [ ] Zero instances of the deprecated `oldFunction()` remain
- [ ] All database queries go through the repository layer
- [ ] Test coverage for refactored modules is above X%

## Motivation & Urgency
### Why Now
The trigger that made this the right time:
- Blocked feature? Scaling issue? Recurring incidents? Team growing?

### Business Case
- **Cost of NOT refactoring**: [Quantified: incidents, velocity loss, hiring friction]
- **Value of refactoring**: [What it unblocks: features, performance, team speed]
- **Time investment**: [Estimated effort in days/weeks]
- **Break-even**: [When the investment pays off]

### Stakeholder Alignment
Who needs to approve this and what they care about (timeline impact, risk, feature delay).

## Scope & Boundaries
### In Scope
Explicitly list what IS being changed:
- Files/modules: [list]
- Patterns/abstractions: [list]
- Dependencies: [list]

### Out of Scope
Explicitly list what is NOT being changed and why:
- [Module X]: Not touched because [reason]
- [Pattern Y]: Separate refactor planned for [timeframe]

### Phases
If the refactor can be broken into independent phases:
- **Phase 1**: [Scope] → [Deliverable] → [Can ship independently: yes/no]
- **Phase 2**: [Scope] → [Deliverable]
- **Phase 3**: [Scope] → [Deliverable]

## Migration Strategy
How to get from current → target state while keeping the system working throughout.

### Approach
- **Strangler fig**: New pattern alongside old, gradually migrate callers
- **Big bang**: One switchover (higher risk, faster completion)
- **Incremental**: Gradual replacement file by file

### Coexistence Plan
If old and new patterns coexist temporarily:
- How are they distinguished? (naming convention, directory, feature flag)
- How long will both exist?
- What prevents new code from using the old pattern?

### Data Migration
If schema or data format changes:
- Migration script approach
- Backfill strategy
- Rollback capability

## Implementation Steps
Ordered list of concrete steps. Each step should leave the codebase in a working, deployable state.

### Format
```
Step 1: [Short description]
Files: [list of files changed]
Migration: [any schema changes]
Verification: [how to confirm it works]
PR size: [small/medium/large]
```

### Step Sequence
1. [First change — usually the new abstraction/pattern]
2. [Migrate highest-value or highest-risk area first]
3. [Continue migration area by area]
4. [Remove old code and dead paths]
5. [Update documentation and tests]

Flag any steps that require team coordination or have deploy ordering constraints.

## Risk Assessment & Rollback
### Risk Matrix
For each risk:
- **Risk**: What could go wrong
- **Likelihood**: Low / Medium / High
- **Impact**: Low / Medium / High
- **Mitigation**: How to prevent or detect early
- **Rollback**: How to revert if it happens

### Common Risks
- Data loss during migration
- Broken integrations with external services
- Performance regression under production load
- Blocked feature work during refactor

### Monitoring
- Error rates to watch during/after deploy
- Performance metrics to compare before/after
- Alerts to set up before starting

### Point of No Return
Identify any steps that cannot be easily reversed (schema migrations, data transformations) and what safeguards to put in place.
